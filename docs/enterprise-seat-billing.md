# Atlas Enterprise seat billing

$3,500 USD per month includes up to 25 named users per billed workspace. Additional purchased seats cost $115 USD per user per month. This is licensed quantity billing, not metered usage. Core and Growth prices are unchanged.

Monthly subtotal before taxes and discounts:

| Purchased users | Additional-seat quantity | Monthly subtotal |
|---|---:|---:|
| 25 | 0 | $3,500 |
| 26 | 1 | $3,615 |
| 30 | 5 | $4,075 |
| 50 | 25 | $6,375 |

## Stripe setup before rollout

1. Retain the Enterprise base recurring price at $3,500 USD monthly with quantity 1. Update its product description to “Includes up to 25 named users. Additional users $115 each per month.” Set `STRIPE_PRICE_ENTERPRISE` to that price ID (existing base-price ID can remain).
2. Create “Atlas Enterprise Additional User”, a recurring USD monthly, flat per-unit price of $115. Use licensed quantity, no usage meter, no tiers, no customer-adjustable quantity. Set Render environment variable `STRIPE_PRICE_ENTERPRISE_SEAT=price_...`. Its quantity is extra purchased seats above 25, never the total user count.
3. Create a dedicated customer portal configuration for Enterprise. Enable payment-method updates, invoice history and cancellation as appropriate. Disable subscription updates (both plan and quantity edits); Atlas controls extra-seat changes and rejects reductions below current member usage. Set `STRIPE_ENTERPRISE_PORTAL_CONFIGURATION=bpc_...` in Render. Core and Growth keep the existing default portal configuration. Enterprise plan changes require Atlas support because the base and add-on must be changed together.
4. Ensure the existing webhook endpoint `/api/stripe/webhook` receives checkout.session.completed, customer.subscription.created/updated/deleted, invoice.payment_succeeded and invoice.payment_failed. Retain the existing signing secret. Test mode and live mode require their own matching prices, portal IDs and keys.
5. Redeploy backend with these values and deploy frontend after reviewing the PRs. This code does not create Stripe products, change environment variables or migrate existing subscriptions automatically.

## Customer behavior

- New Enterprise checkout accepts a total purchased-user count (minimum 25). Checkout includes one base item and, when needed, an extra-seat item of quantity total minus 25.
- Owners/admins manage total purchased capacity from Billing. The recurring subtotal and proration policy are displayed before confirmation.
- Increases invoice prorations immediately. A failed payment or authentication requirement grants no extra capacity; update the payment method through Manage Billing and retry. No silent automatic billing occurs when an invitation is accepted.
- Reductions generate prorated credits for a future invoice, not automatic cash refunds. Capacity cannot fall below occupied memberships. Memberships in disabled/suspended status do not occupy seats; all other roles, including viewers and owners, do.
- Invitations do not reserve capacity. Acceptance and reactivation require an available purchased seat. Removing/ disabling users does not reduce the subscription automatically.
- A per-workspace database lock serializes capacity changes and activations. Retried Stripe requests reconcile current subscription quantities before performing another change. Webhooks retrieve current Stripe state under the same lock.

## Existing customer review

Do not silently add charges to existing subscriptions. Review each Enterprise customer's contract and active member count before rollout. Existing members are not removed. An Enterprise workspace with no add-on starts with 25 capacity; if it already has more members, further activations are blocked until an owner purchases sufficient capacity or the agreement is separately addressed. No retroactive invoice is generated by deployment.

If Stripe already contains an add-on before this release, deliver/retry a subscription update event after deployment to synchronize its capacity. Keep the add-on price ID stable: changing it later requires an explicit subscription migration.

## Verification before production use

- Test 25-, 26-, and 30-user checkout totals, discount/tax handling, declined card and required authentication.
- Test paid increase, retry after success, reduction to 25, webhook retries, wrong-workspace access, and concurrent invite acceptance at the last seat.
- Confirm actual deployed billing screen and webhook signature handling. Automated local tests mock Stripe/Mongo; no live charge was performed.
